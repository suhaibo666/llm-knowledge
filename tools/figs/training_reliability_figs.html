浮点非确定性的五层来源
根源：浮点加法不满足结合律 —— 顺序不固定则比特不固定。自底向上五层，机理各异（问题 1）
根源：(a+b)+c ≠ a+(b+c)
尾数位有限 → 每步舍入路径不同 → 只要加法结合顺序不定，结果就不可能逐比特一致（每种顺序都"合法"，但不可复现）
第 1 层 · 算子内原子操作（atomicAdd 类）
embedding/FA backward、scatter_add：并发线程向同一地址累加，硬件串行化但到达顺序随调度每次不同
第 2 层 · 算子内规约拆分（split-K / autotuning）
M、N 小 K 大时启用 split-K；cuBLAS/cuDNN 按 shape 自动选算法 —— 不同算法 = 不同规约树（今天 algo7、明天 algo3，都"对"）
第 3 层 · 通信库规约（NCCL / HCCL）
AllReduce 是加法树：Ring/Tree/NVLS 形态不同；规模一变规约树必变；在网规约（NVSwitch/SHARP）顺序由链路时序定、软件无法固定
第 4 层 · 动态路由（MoE dispatch / combine）
按 expert 分桶靠排序：不稳定排序使同 expert 的 token 次序每次不同；超容丢 token 依赖此序 → 输入内容级不确定（非 ULP 级）
第 5 层 · 框架级随机性
dropout 种子 / DataLoader 多 worker 交错 / TP 组内 RNG 不同步 / Python hash 随机化 —— 与浮点无关，漏一处则前四层白做
对应治理：第 1 层 sort + segmented reduce 替代 atomicAdd；第 2 层固定 workspace/禁 split-K（CUBLAS_WORKSPACE_CONFIG）；第 3 层锁 NCCL_ALGO=Ring/排除 NVLS；第 4 层稳定排序；第 5 层 RNG tracker。综合"确定性税"约 5%–15%。
算子内 通信规约 MoE 路由 框架状态
低精度长链累加：病与药
有限尾数的两个病 → 树形/成对求和把误差从 O(n) 压到 O(log n)（问题 3）
病：顺序累加 O(n·ε)
"巨大累加器 + 单个小元素"最易吞位：|x| < ulp(S)/2 则被整个吞掉

BF16 顺序 Σ 1000×1.0 = 256
（ulp(256)=2，+1 全被舍掉）
药①：树形 / pairwise O(log n·ε)
递归二分，每层相加两个规模相当的部分和 → 几乎不吞位；每元素只过 log₂n 层舍入

同样 1000×1.0 → 精确 1000
= LongCat"二叉树分段累加"
药②：FP8 两级累加（DeepSeek-V3）
tensor core 累加精度不足（实测 ~14 位，K=4096 误差近 2%）
→ 只连续累 K=128 短链（低精度硬件）
→ 搬到 FP32 寄存器做块间树累加
= "短链 × 外层树"，DeepGEMM 参考实现
工程要点：CUB/单卡 block reduce 内部本就是树形，真正要治的是跨 block / 跨卡 / 跨机的合并顺序 —— 分段树形同时给出更小误差 + 固定顺序，是确定性（问题 1）与精度（问题 3）的交汇解。另有 Megatron --accumulate-allreduce-grads-in-fp32（FP32 main_grad）与 Kahan 补偿求和两条互补路。
SDC / 比特翻转：四层检测体系 + 确定性重放定界
覆盖率与开销逐层权衡；重放是"黄金标准"，但前提是问题 1 的全栈确定性（问题 4）
第 1 层 · 带外筛查（不占训练时间）
已知答案测试 + 应力工况（满功耗/逼近温度阈）；DCGM/EUD、华为 5 层压测（感知率 40%→90%）。筛查 ≠ 训练负载，有漏网
第 2 层 · 在线统计（近零开销，有盲区）
--check-for-nan-in-loss-and-grad + grad-norm spike。盲区：多数真实 SDC 不体现在任何聚合统计量（尾数翻转混在梯度噪声里）
第 3 层 · 在线校验（低开销冗余）
ABFT：校验和以 O(n²) 抓 O(n³) GEMM 的翻转（十字交叉定位）；DP 副本 hash 互查：多数表决直指坏副本。LongCat 只保护 GEMM 类热点算子
第 4 层 · 确定性重放定界（黄金标准）★
Gemini 2.5 split-phase：约 0.25% step 被重放，其中 6% 确认真损坏 —— 没有 bitwise 确定性，这层直接不存在
覆盖率 ↑ · 开销 ↑
第 4 层机制：确定性重放闭环
在线监控发现可疑 step（spike / 梯度异常）
同一批设备上确定性重跑该 step
逐设备比对中间结果 checksum
不复现
哪台两次不一致 → 坏硬件，分钟级踢卡续训
两次一致
合法波动，虚警排除
关键认知：ECC 只保护存储，运算逻辑里的翻转 ECC 管不到。确定性保证了重放"不一致"只可能来自硬件 —— 这是把"全局 spike"裁决成"某台设备坏了"的唯一可靠依据。

隐式故障 hang：症状与病灶的空间分离 + flight recorder 定位
集合通信的阻塞语义：一个 rank 不到齐，其余上万个静静阻塞在同一调用里（问题 6）
难点：症状 ≠ 病灶
症状：全体 rank 卡住
无人报错 · 日志停滚 · GPU 利用率读数甚至还是 100%（SM 自旋等待）
病灶：某 1 个 rank
dataloader 卡慢存储 / host 死锁 / GPU 停摆 / 网卡半死 —— 没发起或没完成本次 collective
兜底=超时看门狗（watchdog + heartbeat 双线程），但默认 10 min、生产常配 30–60 min —— 一次 hang 最低成本就是数千卡时空转。
定位：NCCL Flight Recorder 的 seq 对账
每个 communicator 环形缓冲记录最近 N 次通信的 (seq, 类型, 尺寸, 状态)，常态零开销；watchdog 超时 dump 全体 rank：
rank 0..1022:  seq=182931 (allreduce, completed)
rank 1023:     seq=182930 (completed)  ← 未发起 #182931
────────────────────────────────
结论：rank 1023 在两次通信间的本地代码里卡住
TORCH_NCCL_TRACE_BUFFER_SIZE + TORCH_NCCL_DUMP_ON_TIMEOUT。非通信 hang 再用 ByteRobust 全量栈聚类（多数栈一致=基准，离群簇=嫌疑机）；straggler 用 NVRx 相对打分 / C4 通信可预测性检出。哲学：快速隔离优先于精确定位。
