# 新代码库分析规划与编排 Skill 设计

## 1. 背景与目标

当前 `source-faithful-analysis` 已经较完整地规定了单个分析单元的证据、行文和机制解释方式：
固定源码基线、逐项核验 `file:line`、先讲背景与设计理由，再讲状态、调用链和约束，并要求
代码只作为证据。但把一个陌生代码库转化成成体系的知识域，还存在一个更上游的问题：
**应该分析哪些能力、模块和核心机制，如何划分页职责，什么状态算覆盖完整。**

如果没有独立规划阶段，分析者容易直接按源码目录或最先看到的类开始写，结果是页面边界随
实现文件漂移、概念重复、核心能力遗漏，或者在用户确认前就形成难以调整的文档结构。

本设计新增 `planning-codebase-analysis` skill，负责从一个新的代码库或大型新子域出发，完成：

1. 代码库侦察和源码基线冻结；
2. 能力、架构、生命周期和核心机制的内容发现；
3. 文档目录、页面所有权、编号和实施顺序规划；
4. 向用户提交分析蓝图并等待确认；
5. 确认后逐页编排现有分析与知识库维护 skills；
6. 实施期间维护覆盖度，发生实质性结构漂移时重新确认。

目标不是增加一个固定的代码库章节模板，而是建立一套可复用的“发现什么值得写、如何避免
遗漏和重复、何时可以开始写”的决策过程。

## 2. 方案选择

采用“规划/编排 skill + 单篇执行 skill”的双层方案。

未采用的方案：

- **继续扩充 `source-faithful-analysis`**：会把全库选题、用户确认、多页协调与单篇证据写作
  混在一个上下文中，触发边界不清，也容易边侦察边写页面。
- **只生成一次目录后退出的 planner**：不能在实施中维护概念所有权和覆盖矩阵，源码发现与
  原计划不符时也没有明确的重规划责任。

职责关系如下：

```text
new repository / large new codebase domain
        │
        ▼
planning-codebase-analysis
  reconnaissance → coverage map → document blueprint
        │
        ▼
user approval gate
        │
        ├── one planned analysis unit/page
        │          ▼
        │   source-faithful-analysis
        │
        ├── wiki page/index/changelog mutation
        │          ▼
        │   maintaining-llm-knowledge
        │
        └── formula / figure / Mermaid when actually needed
                   ▼
             corresponding skills
```

这里的“单篇执行”指**一个分析主题或一篇文档**，不是一个源码文件。解释一个机制通常需要跨
文件追踪入口、状态所有者、调用链、断言和测试；按源码文件划分会重新退化为逐函数转述。

## 3. Skill 边界与触发条件

### 3.1 使用 `planning-codebase-analysis`

在以下情形触发：

- 用户给出一个新的代码仓库，希望分析整体架构、模块和核心机制；
- 用户希望把一个大型代码库或大型新子系统转化成多篇 Wiki/知识库页面；
- 尚未确定页面目录、概念所有权、分析范围和实施顺序；
- 现有页面需要做知识域级重规划，而不仅是重写其中一篇。

### 3.2 不使用该 skill

- 用户只问某个明确函数、机制或已知子系统如何工作；
- 已有用户确认的分析蓝图，现在只需要完成其中一篇页面；
- 只做单页编辑、索引维护、公式或图片修改；
- 用户只是要运行、配置或修复代码，并不要求形成分析交付物。

当一个全新代码库请求同时匹配两个 skill 时，planner 先运行；在蓝图确认后，再为每个页面
调用 `source-faithful-analysis`。不得并行跳过确认门直接写正文。

## 4. 从零侦察的内容模型

planner 先建立内容地图，而不是先发明文件名。以下是发现维度，不是固定章节；不适用的维度
可以标记为 N/A，但必须说明判断依据。

| 发现维度 | 必须回答的问题 | 主要证据入口 |
|---|---|---|
| 定位与外部契约 | 代码库解决什么问题，用户通过哪些入口获得哪些能力 | README、官方文档、examples、public API、CLI/server entry |
| 能力树 | 一级能力及其组合、依赖和可选路径是什么 | public API、配置 schema、registries、feature tests |
| 静态架构 | 哪些职责层/模块承担这些能力，依赖方向和边界是什么 | package skeleton、factories、orchestrators、interfaces |
| 动态生命周期 | 代表性任务如何从配置/请求走到执行和结果可见 | entry point、main loop、scheduler、state transition |
| 状态与数据模型 | 哪些对象、存储和缓存拥有关键状态，必须维护什么不变量 | dataclasses、stores、asserts、serialization、tests |
| 核心机制 | 哪些算法、状态机、调度、并发或资源管理设计承载主要价值 | hot path、control loop、critical data structures |
| 变化与扩展 | 配置、插件、后端、模型或平台差异在哪些边界被吸收 | registries、protocols、backend selection、fallbacks |
| 工程边界 | 性能、内存、并发、分布式、可靠性和观测约束是什么 | benchmarks、guards、error paths、metrics、recovery tests |
| 演进状态 | 哪些路径是当前主干、legacy、实验性或正在迁移 | git history、deprecations、feature flags、design docs |

侦察必须先识别“用户能力”，再映射到源码模块。源码目录只提供查找线索，不能直接成为 Wiki
目录或页面边界。planner 应选择少量代表性生命周期覆盖主要能力；不得为了覆盖所有文件而制造
没有独立设计命题的页面。

## 5. 分析蓝图契约

在开始写任何 Wiki 正文前，planner 向用户提交一份蓝图。蓝图至少包含以下部分。

### 5.1 仓库级结论

- 仓库、branch、commit 和冻结日期；
- 目标读者和知识库落点；
- 一到两句话的系统中心命题；
- 当前主路径与 legacy/experimental 路径的边界；
- 侦察中仍无法从源码确认的问题。

### 5.2 三张内容地图

1. **能力地图**：用户可见能力以及它们的依赖关系；
2. **静态架构地图**：职责层、模块边界、依赖方向、状态所有者；
3. **动态生命周期地图**：一到数条代表性任务如何跨越这些边界。

地图在确认阶段可以是表格或简洁 Mermaid/ASCII；此处用于规划，不要求提前制作最终页面配图。

### 5.3 文档目录与页面计划

每个候选页面都必须给出：

| 字段 | 要求 |
|---|---|
| 路径与标题 | 遵守现有 Wiki 功能树和目标目录命名习惯 |
| 页面类型 | Overview / Guide / Deep Dive；由读者问题决定，不机械套模板 |
| 中心命题 | 该页解释的一个主要设计判断 |
| 读者问题 | 读完后能够回答的具体问题 |
| 内容所有权 | 由该页权威解释的能力、状态或机制 |
| 明确不包含 | 应链接到其他页面而不在本页重复的内容 |
| 核心机制 | 需要深入解释的状态机、数据结构、算法或控制流 |
| 证据入口 | 初步核验过的关键文件、符号、测试或设计文档 |
| 依赖关系 | 阅读前置、交叉链接和实施顺序 |
| 图表候选 | 只有关系难以用线性文字说明时才规划 |
| 完成标准 | 本页怎样证明已讲清机制而不是搬运源码 |

编号根据现有目录约定、阅读依赖和页面职责确定。架构概览通常位于入口段，但不得因为某功能
当前最受关注就机械占用 `01`；也不得用固定编号段替代内容判断。

### 5.4 覆盖矩阵

蓝图必须把“能力/生命周期/核心机制”映射到权威页面：

| 内容项 | 权威页面 | 其他页面允许保留的内容 | 状态 |
|---|---|---|---|
| 请求调度 | `scheduler_analysis.md` | 调用方只保留输入输出契约和链接 | planned |

一个概念只能有一个主要所有者；其他页面只保留理解本页所需的边界说明和链接。覆盖矩阵同时
用于发现遗漏：存在关键能力或状态所有者却没有页面承接时，蓝图不能进入实施。

### 5.5 实施顺序

实施顺序根据认识依赖确定，而不是按文件名机械递增：

1. 选择一个能校准术语、证据密度和机制解释方式的标杆页；
2. 完成架构主线和高连接度的核心机制页；
3. 展开专项能力、后端和横向工程页面；
4. 最后收敛 overview/index，消除重复并校准全局链接。

标杆页可以是架构概览，也可以是最能暴露状态所有权的核心机制页，由仓库实际结构决定。

## 6. 用户确认门与重规划条件

planner 展示蓝图后必须停止，等待用户明确确认目录、页面边界、编号和范围。在确认前允许只读
侦察，不创建、重命名或重写 Wiki 页面。

用户确认后，将多页面蓝图记录到 `docs/superpowers/specs/`，作为跨页面、跨会话的实施合同；
它不取代 Wiki 功能树，实施完成后的页面和各级 `index.md` 仍是内容权威。范围很小且能在同一
对话完成的计划可以只保留在确认消息中，不机械制造 spec 文件。

默认只有一次总蓝图确认。实施期间只有以下实质变化需要重新确认：

- 需要新增或删除一组页面，而非页内小节调整；
- 核心概念的权威页面发生变化，影响多个页面边界；
- 目标 Wiki 目录需要新建或迁移；
- 冻结基线必须改变；
- 源码证据推翻了蓝图的系统主线或主要模块划分；
- 分析范围、目标读者或交付形式需要扩大。

文件名微调、页内结构优化、定位符更新和不影响所有权的交叉链接不触发第二次确认，但应在
阶段进度中说明。

## 7. 确认后的实施编排

蓝图确认后，planner 继续作为协调者，但不复制下游 skills 的写作规则。

- 每个页面把蓝图中的中心命题、所有权、不包含内容、证据入口和完成标准传给
  `source-faithful-analysis`；后者跨源码文件完成事实核验与机制写作。
- 任何 Wiki 页面、目录、index 或 changelog 变更调用 `maintaining-llm-knowledge`。
- 公式、普通图和 Mermaid 仅在页面实际需要时调用对应 skill。
- 大型计划可以按无共享文件冲突的页面分波并行；共享 index、overview 和 changelog 由协调者
  统一收敛。
- 每一波结束后更新覆盖矩阵，检查概念重复、术语漂移、定位符真实性和计划外缺口。

planner 不以页面数量、行数或代码块比例判断进度。完成依据是：计划中的核心能力、代表性
生命周期、状态所有者和机制都有权威页面，页面之间没有两份完整真相来源，并通过知识库门禁。

## 8. 与现有 skills 的变更边界

实施本设计预计涉及：

- 新增 `skills/planning-codebase-analysis/SKILL.md`；
- 视篇幅决定是否新增 `references/analysis-blueprint.md`；只有模板显著挤占入口 skill 时才拆；
- 更新 `CLAUDE.md`、`AGENTS.md` 和 `skills/README.md` 的按需加载路由；
- 收窄 `source-faithful-analysis` 对“全新、多页面 codebase 分析”的触发说明：无已确认蓝图时先
  调用 planner；
- 在 `references/codebase.md` 明确它执行的是单个分析单元/页面，而非单个源码文件；
- 保留其中的静态/动态架构写法、五拍、源码证据和删除测试，不在新 skill 中重复。

`source-faithful-analysis` 对论文、规范、数据集和单次问题的现有能力不受影响。新 planner 第一版
只负责 codebase；不为了形式对称扩展到所有来源类型。

## 9. 失败处理与安全边界

- 找不到足够源码或历史证据时，蓝图标注未知和推断，不用训练记忆补齐模块。
- 仓库过大时先提出分域方案，用户确认当前分析域后再展开，不假装一次覆盖所有内容。
- 目标 Wiki 已有相关页面时，先建立复用/重写/合并表，不默认新增重复页面。
- 工作区存在未提交修改时，只读侦察不改动；实施时逐文件增量合并，不 reset、stash 或覆盖。
- 源码仓库只读，基线冻结后不随 `origin/main` 自动移动。
- 计划不能由并行 writer 自行改变；发现实质漂移时返回协调者处理确认门。

## 10. 验收与测试

### 10.1 Skill 行为验收

至少使用以下场景做前后对照测试：

1. **全新大型框架**：输入只有仓库路径和“分析架构/模块/核心机制”，应先产出能力地图和蓝图，
   不直接写页面。
2. **明确单机制问题**：输入指向一个 scheduler/cache/compiler pass，应跳过 planner，直接使用
   单篇分析 skill。
3. **已有确认蓝图**：应按一个页面合同实施，不重新发明目录。
4. **目录诱导场景**：源码目录看似分层但状态所有权跨目录，应按职责重构内容地图。
5. **计划漂移场景**：源码证据推翻两个页面边界，应停止相关实施并请求重新确认。
6. **大型仓库压力场景**：不得为了显得覆盖完整而把每个目录规划成页面。

成功标准是触发路由稳定、确认门不被绕过、蓝图能发现能力遗漏和概念重复，并且下游页面合同
足够明确，使 writer 无需重新决定页面职责。

### 10.2 静态与仓库检查

- 使用 skill validator 检查新增/修改的 skill frontmatter 和结构；
- 检查所有 reference 可从入口 skill 到达且不重复维护同一规则；
- `git diff --check`；
- `python tools/check_links.py --strict`；
- `python tools/check_math.py --changed --strict`；
- `python -m pytest tools/`；
- `npm run docs:test`。

## 11. 非目标

- 不定义所有代码库都必须拥有的固定页面列表；
- 不规定固定层数、页数、行数、代码引用数量或编号段；
- 不替代单篇源码分析、Wiki 维护、公式和制图 skills；
- 不自动修改源码仓库；
- 不在用户确认蓝图前创建正文页面；
- 不把实施 spec 或覆盖矩阵变成 Wiki 功能树之外的第二套长期内容权威。
