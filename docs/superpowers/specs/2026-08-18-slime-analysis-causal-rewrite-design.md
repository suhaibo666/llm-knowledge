# slime 分析系列因果化重构设计

## 1. 目标与验收口径

本次重构覆盖 `wiki/02_engineering/04_posttrain_frameworks/slime/` 下 21 篇内容页、目录 `index.md` 与 `wiki/changelog.md`。目标不是给现有页面机械增加“设计背景”小节，而是把整个系列从“对象、参数和调用链的罗列”改造成可解释的系统设计分析：读者先知道问题为何出现，再理解约束如何逼出设计，随后沿真实调用链验证机制，最后能判断方案的适用边界与代价。

每篇页面都必须回答六个问题：

1. 没有该模块时会出现什么具体问题或失败模式；
2. 哪些系统约束与不变量限制了解法；
3. slime 选择了什么核心设计，为什么它适配这些约束；
4. 设计如何通过对象、状态、调用链和数据流落地；
5. 显而易见的替代方案为什么没有被采用；
6. 当前设计付出了什么代价，在哪些条件下退化、回退或失效。

验收时不以“新增多少段文字”为标准，而以读者能否从问题推导到实现、并能区分事实与推断为标准。

## 2. 证据模型

页面采用三层证据，并明确区分其认识论地位：

- **源码事实**：来自钉死 commit 的实现、测试、断言、注释、配置默认值和状态转换；所有非平凡事实使用 fixed-commit `file:line` 链接。
- **项目/社区文档事实**：来自同一基线的 README、官方文档、examples、官方 issue/PR/design note；引用时说明它是在描述目标、使用方法还是兼容边界，不能用文档愿景替代源码行为。
- **分析判断**：根据约束、失败路径、测试和实现形态推导出的设计动机或取舍。使用“由此可推断”“这意味着”“设计上可以理解为”等措辞，不写成作者原话。

发生冲突时，以钉死基线的源码行为为准，并显式记录“文档所述”与“实现实际”之间的差异。第三方博客只用于发现线索，不作为机制结论的唯一证据。

## 3. 统一因果骨架

页面保留与主题匹配的自由结构，但正文必须形成以下因果链：

1. **结论先行**：一段话说明该模块解决的问题、核心设计选择和关键代价。
2. **问题背景**：从训练/推理系统中的冲突、资源约束或正确性风险切入，不从类名切入。
3. **约束与不变量**：列出设计不能破坏的条件，例如 on-policy 版本边界、拓扑映射、rollout 身份、显存时分复用或 loss 归一化语义。
4. **为什么这样设计**：比较至少一个直观替代方案，解释当前方案的收益与代价。
5. **机制落地**：沿入口、关键对象、状态机、数据结构和真实调用链展开；机制段必须回扣前述约束。
6. **边界与失败模式**：说明回退条件、断言、兼容路径、观测信号和常见误读。
7. **Related Pages**：保留 3–7 个精选双向链接，每条说明关系。

不是每篇都必须使用完全相同的标题。quickstart 仍以“最短可运行路径”为主，但需要解释默认配置背后的系统假设；专题页仍以专项机制为主，但开头必须建立问题与约束。

## 4. 页面职责与核心设计命题

| 页面 | 设计背景/问题 | 必须讲透的核心设计命题 |
|---|---|---|
| `01` 架构总览 | 原生训练、推理引擎能力强但生命周期和数据语义不同 | slime 选择薄编排层而非统一最低公分母 engine abstraction |
| `02` quickstart/config | 参数跨 Ray、Megatron、SGLang 三个命名空间，错误常在运行后期才暴露 | 配置归一化与校验是系统装配协议，不只是 CLI 选项表 |
| `10` 端到端迭代 | rollout、训练和权重版本存在闭环依赖 | iteration 是带版本边界的阶段事务；async 是边界移动而非删除边界 |
| `11` Ray 控制面 | 分布式对象的所有权、资源放置和批量调用容易混淆 | group/manager/server/engine 分别承担资源、协调、服务与执行职责 |
| `12` Sample/DataSource | 异构 rollout、续生成、工具调用与 trainer tensor ABI 冲突 | 语义对象、队列生命周期和训练 dict 三层分离，以守住身份与可回收性 |
| `13` SGLang rollout | 高并发生成既要吞吐又要保留请求级身份和策略元数据 | engine server 化、router 与 manager 调度分层；partial/streaming 是状态协议 |
| `14` Megatron training | RL 样本语义与 Megatron batch/并行执行接口不一致 | actor 封装转换与角色复用，训练内核仍保持 Megatron-native |
| `15` loss/并行 | token、sample、group 归一化与 DP/CP/PP 切分容易改变目标函数 | loss reducer 明确统计口径，并把并行切分约束绑定到还原/归一化过程 |
| `16` 权重同步 | 训练 shard topology 与推理 shard topology 不同，更新中还要避免半版本 | 将同步视为带 pause/flush/version 的提交协议，transport 只是数据面 |
| `17` 训推一致性 | 相同权重仍可能因输入、采样、kernel 与 routing 不同而产生偏差 | 一致性分层定位，而非把所有误差归因于权重同步 |
| `18` 容错与观测 | 故障域跨控制面、engine、数据与训练，不适合单一全局事务 | 按故障域恢复，配合可重放数据与分层观测缩小恢复范围 |
| `19` rollout backend 扩展 | “external engine”与“新 backend”容易被误认为同一扩展层 | 区分部署位置变化和协议实现变化，明确最小稳定接口与泄漏的原生能力 |
| `20` OPD | teacher 信号需要进入 on-policy rollout，但不应复制一套训练系统 | teacher 作为可选角色接入同一 Sample/训练 ABI，以 reverse-KL advantage 复用 actor 路径 |
| `21` speculative/MTP | 在线训练希望获得推测解码收益，但 draft 状态和主模型版本会漂移 | MTP 作为同版本耦合能力参与 rollout/同步，而不是独立静态 draft 服务 |
| `22` 低精度 | 训练计算、参数存储、通信与 rollout 量化有不同误差和兼容边界 | 拆分精度轴并分别校验，避免一个 dtype 开关掩盖多套数值语义 |
| `23` 模型架构扩展 | Megatron 与 HF/SGLang 对同一架构使用不同命名、切分和加载约定 | 扩展的核心是双向语义映射与能力注册，不是只增加 model class |
| `24` Agent 工作流 | 多轮工具环境产生树状执行，而 trainer 仍需要线性训练 fragments | agent runtime 留在 rollout 数据面，通过 rollout id/compact fanout 映射到训练统计 |
| `25` vime/vLLM | 衍生实现换掉 rollout engine 后，哪些 slime 设计仍成立、哪些协议被改写 | 以部署/请求/同步/容错四条契约对照，不把 fork 差异误写成 upstream 能力 |
| `30` rollout 优化 | 吞吐瓶颈可来自服务容量、调度空洞、长尾和训练等待，单看 tok/s 会误判 | 用容量账本和关键路径定位瓶颈，再选择并发、PD、overlap 或过滤策略 |
| `31` 稳定性 | RL 训练的数值、数据、策略版本与系统故障相互放大 | 将稳定性分成可观测的不变量与控制回路，区分症状抑制和根因修复 |

## 5. 重构顺序

采用“标杆页校准 + 分波次推广”：

1. 先重写 `12_slime_sample_datasource_analysis.md`。它直接暴露当前缺陷，且连接 rollout、agent、训练、容错四个主题，适合作为结构与语言标杆。
2. 重构主链路页：`01`、`02`、`10`、`11`、`13`–`18`。
3. 重构能力扩展页：`19`–`25`。`25` 单独核验 vime/vLLM 的源码与官方文档基线。
4. 重构横向工程页：`30`、`31`。
5. 最后更新 `index.md`，用“问题 → 模块 → 设计选择 → 页面”导航替代纯功能清单，并在 `changelog.md` 记录重构范围与证据基线。

页面边界默认保持不变。只有页面超过 500 行或出现真正的主题重叠时才触发拆分/合并；本轮不为追求结构统一而改名。

## 6. 并行写作与一致性控制

`12` 由主协调者完成并校准。之后每个独立页面可交给一个 writer agent，但必须共享同一页面契约：只改一个文件、打开并核验每个定位符、明确区分事实与推断、遵守本设计的核心命题。每一波结束后由主协调者抽查至少 2–3 个定位符、核对跨页术语和删除重复叙述，再开始下一波。

跨页概念设唯一权威页：控制对象归 `11`，Sample/DataSource 语义归 `12`，rollout 请求状态归 `13`，Megatron 执行归 `14`，loss 统计归 `15`，权重提交归 `16`，一致性归 `17`。其他页面只概括并链接，不复制完整机制。
