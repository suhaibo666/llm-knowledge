### P0

**P0-1｜18 §5.1“PP 可以只发送本 TP rank 的切片，再在接收 stage 重建”**
- 页面原文：“并且带 `assert not self.use_v2_model_runner`——**这是 MRV1 独有的分支**，与 §7.1 ‘MRV2 拒绝 PP’的结论互为印证。”
- 源码证据
  - MRV2 支持 PP：`vllm/v1/worker/gpu/model_runner.py::GPUModelRunner.__init__` 设 `self.use_pp = pipeline_parallel_size > 1`，并构造 `PPHandler`；18 页 §5.2 讲的就是这条 MRV2 通道。
  - §7.1 拒绝 PP 的是 **MRV2 的 DBO**（`vllm/config/vllm.py::VllmConfig._get_dbo_unsupported_features` 追加 "dual batch overlap with pipeline parallelism"），以及 MRV2 PCP（`PCPManager.validate_config`）。
  - 该 assert 的直接原因是 V2 不支持 sequence parallelism：`VllmConfig` 的 V2 unsupported 列表在 `enable_sp and TP>1` 时加入 "sequence parallelism"。另外 V2 只拒绝 "pipeline parallelism with external_launcher"。
- 影响：读者会以为 MRV2 不能跑 PP，并与本页 §5.2 自相矛盾。
- 修正：删除“MRV2 拒绝 PP”的印证句，改为“该分支需要 SP residual scatter，而 MRV2 不支持 SP（TP>1）；MRV2 支持 PP，只有 DBO/PCP 与 PP 互斥，以及 external_launcher+PP 不支持”。

**P1-1｜18 §1.2 ⑥、§1.3 ⑥、§5.2“sampled token 走独立的 PP 反向同步通道”**

- 源码证据：`vllm/v1/worker/gpu/pp_utils.py::PPHandler` / `compute_need_sampled_mask` 只被 `vllm/v1/worker/gpu/model_runner.py` 引用。MRV1 `vllm/v1/worker/gpu_model_runner.py` 没有这条 sibling-group 反向广播，只有 external_launcher 下的 `broadcast_pp_output`（`broadcast_tensor_dict(src=last)` 广播 logits）。

**P1-2｜25 §6.1“session cleanup 不是参数 rollback”**
- 页面原文：“Ray Executor 的收集方式不同：它为所有 Worker 建立 object refs，再以 `ray.get(refs, timeout=...)` 等待……因此没有 MultiprocExecutor ‘遇到首个失败后留下后续本地响应队列未 drain’的同一实现问题。”
- 源码证据
  - 这只对 `vllm/v1/executor/ray_executor.py::RayDistributedExecutor.collective_rpc` 成立。
  - `distributed_executor_backend="ray"` 且 `VLLM_USE_RAY_V2_EXECUTOR_BACKEND` 时，`Executor.get_class` 选中 `vllm/v1/executor/ray_executor_v2.py::RayExecutorV2(MultiprocExecutor)`。它的 docstring 写明“reuse the MQ-based control plane”，且没有重写 `collective_rpc`，因此首个失败即退出、未 drain 的语义与 MP 完全相同。
- 修正：按 `Executor.get_class` 枚举 Ray V1 与 V2，分别说明收集语义。

**P1-3｜25 §4.2“公开调用链”（hop-walk）**
- 页面原文：“`AsyncLLM.collective_rpc` → `EngineCoreClient.collective_rpc_async` → `EngineCore.collective_rpc`”
- 源码证据
  - `vllm/v1/engine/core_client.py::AsyncMPClient.collective_rpc_async` 实际调用 `call_utility_async("collective_rpc", ...)`，经 ZMQ utility 消息进入 EngineCore 进程的输入线程与 busy loop，才到 `EngineCore.collective_rpc`。这一跳是进程边界。
  - internal/hybrid DP 下，`DPLBAsyncMPClient.call_utility_async` 对**所有** `core_engines` 做 `asyncio.gather`，只返回 `[0]`；external LB 的 `DPAsyncMPClient` 只发给自己的 engine。
  - `pause_scheduler_async`、`set_weight_version_async` 同理。
- 影响：DP 部署下，“finish 成功返回”的真实含义是跨 Engine 的 gather（任一 engine 抛错即传播），版本标签也会写到每个 engine。§5.3 只说“外部 LB 不自动加入共识”，没有交代内部 DP 的扇出。
- 修正：调用树补 utility 跳，并标 `[进程边界]` 与 `[DPLB: gather 全部 engines]`；链接 13 §3.1/§3.2 的 client 变体。

**P1-4｜26 §1 / §8.4 适用范围与变体集合**
- 页面原文：“适用范围：V1 `MultiprocExecutor`、本机 `WorkerProc`……”；“它不替代 Ray 的多节点调度”。
- 源码证据
  - (a) 页面没有从 `Executor.get_class`（六分支）和 `ParallelConfig.__post_init__`（默认 backend 选择：`nnodes>1` 时选 mp，device_count 不足时报错，placement group 存在时选 ray）给出本执行器何时被选中的依据。
  - (b) `MultiprocExecutor._init_executor` 还支持 DP 内多节点：`node_rank_within_dp>0` 的 follower 不建 `rpc_broadcast_mq`，`collective_rpc` 会 assert 失败；leader 通过 `peer_worker_response_mqs` 读远端响应；远端 reader 走 ZMQ XPUB，不受 ring 背压；多节点响应队列是 `create_single_reader_mq_broadcasters(1<<22, 6)`。13 §4.1 的 headless 分支正依赖这条路径。
  - (c) `RayExecutorV2` / `RayWorkerProc(WorkerProc)` 复用本页整套广播、Future 与响应控制面。
- 修正：新增一小节“哪些执行器使用这套控制面”，列出选择点和上述三类变体；把 §5 的容量与背压结论限定为“本机 leader、local reader”，并命名远端 reader 的差异。

**P1-5｜26 §4.2“全员回复只在成功路径上构成 barrier”与 §6“Future FIFO”**（静态推导）
- 页面原文：“遇到第一个 `FAILURE` 就立即抛错，不再消费其后的队列”；“某条路径若私自多发或少发一个 response，后续 Future 都可能错位。”
- 源码证据：`MultiprocExecutor.collective_rpc::get_response` 在 rank i 失败或 `dequeue(timeout)` 超时后直接 raise，rank>i 的响应（或超时后迟到的响应）仍留在 `response_mqs`。下一次 RPC 按队首读取，会读到这条陈旧响应。
- 问题：页面把“未 drain”和“FIFO 错位”分开陈述，没有指出本页自身的失败/超时路径就是破坏配对的来源。25 §6.1 的恢复建议（保持 pause、重建 ranks）也没有提示“复用该 executor 可能错配”。
- 修正：在 §6 加一条不变量破坏场景，标“分析推断”；给出处置建议：部分失败后要么重建 executor/engine，要么证明所有队列已 drain。
