## 4. 发现（编号，按严重度）

### P0

**F1 — 19 §7.3、§7.5：MRV1 派发入口用了不存在的符号，并漏掉真实的选择逻辑**
- 页面原文：§7.3“`_dispatch_cudagraph` 返回的 `(mode, batch_desc)` 被写入 forward context”；§7.5 调用树 `GPUModelRunner._dispatch_cudagraph(...)  # MRV1`。
- 源码证据：
  - `grep -rn "_dispatch_cudagraph" vllm/` 零命中。
  - 真实入口是 `vllm/v1/worker/gpu_model_runner.py::GPUModelRunner._determine_batch_execution_and_padding`，内部闭包 `dispatch_cudagraph(num_tokens, disable_full, valid_modes)` 调 `CudagraphDispatcher.dispatch`。
  - 先 `_pad_for_sequence_parallelism`；`disable_full=use_cascade_attn or has_encoder_output` 传成 `invalid_modes={FULL}`。
  - DP>1 时调 `coordinate_batch_across_dp`，再以 `valid_modes={CUDAGraphMode(synced)}` 重派发，并断言 token 数一致。
  - `force_eager` 时 `valid_modes={NONE}`。
- 影响：页面契约（index）明确包含“两代 Runner 的派发”，读者按页面符号进不了源码；FULL 被 cascade/encoder 禁用、DP 重派发这些分支，11 与 19 都没有交代，形成 E2E 断链。
- 修改建议：
  - 把 §7.3/§7.5 的入口改为 `_determine_batch_execution_and_padding → dispatch_cudagraph → CudagraphDispatcher.dispatch`。
  - 补一小段：SP padding、`invalid_modes`（cascade、encoder 输出）、`force_eager`、DP 协商后重派发。
  - 在 11 §2.6.1“执行模式”行链接到该小节。

### P1

**F2 — 19 §1.2 图 1：sampled token 回写对象画错，与 12 §2.6 矛盾**
- 页面原文：“核心不变量——**采样出的新 token 写回同一 `InputBuffers` storage**”；图中边为 `SMP -->|sampled token ids 同址写回| BUF` 和 `BUF -->|下一步的 num_tokens 与 num_reqs| RUN`。
- 源码证据：
  - `vllm/v1/worker/gpu/model_runner.py::GPUModelRunner.postprocess_sampled` → `input_batch.py::post_update` 写的是 `req_states.last_sampled_tokens`、`req_states.all_token_ids.gpu`、`total_len`、`num_computed_tokens`。
  - `input_batch.py::InputBuffers.__init__` 只有 `input_ids / positions / is_padding / query_start_loc / seq_lens / dcp_local_seq_lens`。
  - 下一步由 `combine_sampled_and_draft_tokens` 把 `last_sampled_tokens` 拷进 `input_buffers.input_ids`。
  - 下一步的 `num_tokens/num_reqs` 来自新的 `SchedulerOutput`，不是来自 buffer。
- 修改建议：回边改为 `SMP → RequestState(last_sampled/all_token_ids)`，再加 `RequestState → prepare_inputs(combine kernel) → BUF.input_ids`；`num_tokens` 的来源改回 SCH。不变量应表述为“持久 storage 地址不变，值每步由 prepare_inputs 重写”。

**F3 — 19 §6.5 图 2：启动时间轴顺序错误，与 12 §2.9 矛盾**
- 页面原文：`B["runner 初始化后解析能力 resolve_cudagraph_mode_and_sizes"] -->|resolved CUDAGraphMode| C["首次 dummy forward Dynamo trace 与 compile_all_ranges"] --> D[profile_cudagraph_memory] --> E[真实 KV 分配]`。
- 源码证据：
  - `vllm/v1/engine/core.py::EngineCore._initialize_kv_caches` 先 `determine_available_memory`。
  - `Worker.determine_available_memory` 调 `GPUModelRunner.profile_run → _dummy_run(skip_attn=True, is_profile=True)`，首次 trace/compile 发生在这里。
  - `resolve_cudagraph_mode_and_sizes` 只在 `GPUModelRunner.initialize_kv_cache` 中调用：先由 `profile_cudagraph_memory → _init_minimal_kv_cache_for_profiling → initialize_kv_cache(is_profiling=True)` 调一次，真实初始化时再调一次。
  - 所以 C 在 B 之前，B 实际出现两次（D 内与 E 内），首编译时看到的是 `__post_init__` 定稿但尚未 resolve 的 mode。
- 修改建议：顺序改为 A → C(profile_run) → D(含 minimal KV + resolve#1) → E(真实 KV + resolve#2) → F → G → H；删去 B→C 的“resolved CUDAGraphMode”标签。
- 可选补充：没有 KV cache 的模型或 elastic EP 扩容启动会跳过 C/D，首编译推迟到 F。

**F4 — 11 §1.4、12 §1.5：异步调度（默认）必然启用 batch queue，两页都没说；闭环图与“差别清单”在默认配置下失真**
- 页面原文：
  - 11：“普通 `EngineCore.step()` 先 schedule()……`execute_model()` 返回 `None` 时 Core 再调用 `sample_tokens`”；时序图含 “async 时输出线程调用 get_output”；“从 runner 侧看只有四处差别”。
  - 12：“下图沿 `EngineCore.step()` 走一轮……Core 见到 `None` 才调 `sample_tokens(grammar_output)`”；“从 runner 侧只看得到五点差别”。
- 源码证据：
  - `vllm/config/vllm.py::VllmConfig.max_concurrent_batches`：async 下 MRV2 为 `pp+1`，MRV1 在 pp≤1 时为 2，否则为 pp，所以 async ⇒ 恒 ≥2。
  - `EngineCore.__init__` 在 `batch_queue_size > 1` 时选 `step_with_batch_queue`。
  - `VllmConfig.__post_init__` 在未指定时对生成模型默认 `async_scheduling=True`。
  - `EngineCore.step_with_batch_queue` 在 `pending_structured_output_tokens` 为假时，提交 `execute_model(non_block)` 后**立即** `get_grammar_bitmask` 并 `sample_tokens(non_block=True)`，不等 execute 结果，也不检查 `None`。
  - 另外：MRV1 的 `GPUModelRunner.sample_tokens` 在状态为空时返回 connector-only 输出而不是 `None`，所以 11 第 4 点的 `None → exec_model_fut.result()` 分支对 MRV1 实际不可达。
- 影响：默认服务配置下读者会以为 runner 先完成 execute 才收到 sample 请求。11 的时序图描绘了“async + `step()`”这种基线中不存在的组合。
- 修改建议：两页开头各加一句“async 调度（默认）⇒ `max_concurrent_batches≥2` ⇒ Core 走 `step_with_batch_queue`”。差别清单首条改为“`sample_tokens` 紧随 `execute_model` 以 non_block 提交，worker 按 RPC 顺序串行消费”。把 11 时序图的 async 注记挪到 batch-queue 版本，或把图标注为“非 async/非 PP 时的 `step()`”。

**F5 — 19 §4.3（及 §9.1 `compile_sizes` 行）：`compile_sizes` 与 capture 阶梯必须对齐的“硬约束”只在 MRV1 生效**
