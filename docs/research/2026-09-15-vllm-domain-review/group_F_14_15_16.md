### 1.3 Findings（页 14）

**F14-1 [P0] §4.5「有 draft 时，整个普通 Sampler 被绕过」（连带 §1.3 表“spec 路径绕过普通 sampler”行、§2.1 末句、§4.4 表第 4 行、§4.5「成本与阻断」、§7.1 调用树）**

- 页面原句：“所以有 draft 时 `Sampler.apply_sampling_params` 一行都不执行——allowed mask、penalties、bad words、thinking budget、temperature、min-p、top-k/top-p 全部不在这一步发生”；§2.1：“普通 sampler 被绕过时这些 kernel 也不执行”。
- 源码证据：
  - `vllm/v1/worker/gpu/spec_decode/rejection_sampler.py::RejectionSampler._verify` 第一步就是 `processed_logits = self.sampler.apply_sampling_params(logits, expanded_idx_mapping, idx_mapping, idx_mapping_np, pos, draft_sampled, expanded_local_pos)`，然后才 `rejection_sample(processed_logits, ...)`。bias、penalties、bad words、thinking budget、temperature、min-p、top-k/top-p 全部作用在 target 行上。
  - V1 同样不是“整体绕过”：`vllm/v1/sample/rejection_sampler.py::RejectionSampler.forward` 用 `self.sampler(logits=bonus_logits, ..., predict_bonus_token=True)` 通过**普通 Sampler**采 bonus；target 行走 `self.apply_logits_processors(...)` 加 `apply_sampling_constraints(...)`。
  - 页面自己的 §2.1 就有矛盾：penalties/bad-words kernel 读 `expanded_local_pos` 计入窗口内更早的 draft。只有 spec 路径上 `expanded_local_pos>0`，而 spec 路径正是 `RejectionSampler._verify` 把 `draft_sampled` 当 `input_ids` 传进去的地方。
  - 16 §7 与 §10.1 的写法是对的（`_verify -> Sampler.apply_sampling_params # 归 14`），所以两页直接矛盾。
- 影响：读者会以为投机下 temperature、top-k/top-p、penalties 都不生效，p 的构成没人负责（16 §1 把“p 由哪些约束构成”交给 14）。§4.5 把 min_p/logit_bias 的“能力损失”说成是“绕过 sampler”造成的也不对。真正原因是 `SamplingParams._validate_spec_decode` 在入口拒绝，V1 `build_logitsprocs` 只构建 `MinTokensLogitsProcessor`。
- 建议修正：把 §4.5 改写为“被替换的只是**选择步骤**（`gumbel_sample`/`flashinfer_sample` → `rejection_sample`）和选择之后的数据面（trace replay、sampling mask、`logprob_token_ids`）。`apply_sampling_params`（MRV2）/ `apply_logits_processors + apply_sampling_constraints`（V1，bonus 另走完整 `Sampler.forward`）仍在 target 行上构造 p，而且 penalties/bad-words 按 `expanded_local_pos` 感知窗口历史”。同步修改 §1.3 行、§2.1 末句、§4.4 表行和 §4.5「成本与阻断」的因果。§7.1 调用树里 `RejectionSampler.__call__` 下补 `_verify_in_chunks -> _verify -> Sampler.apply_sampling_params`。

**F14-2 [P2] §6.4「draft 在进入下一步之前就被 grammar 预筛过一遍」＋ §1.2 图边“经 validate_tokens 过滤并以 -1 补齐”**

- 页面原句：“`Scheduler.update_draft_token_ids_in_output`（以及 `update_draft_token_ids` 的对应位置）……被截掉的尾部用 `-1` 补齐到原本调度的位置数，个数记进 `scheduler_output.num_invalid_spec_tokens`”。
- 源码：`vllm/v1/core/sched/scheduler.py::Scheduler.update_draft_token_ids`（同步 `post_step` 路线）只做 `request.spec_token_ids = grammar.validate_tokens(...)`，即**截断**，不补 `-1`，也不写 `num_invalid_spec_tokens`。补 `-1` 并计数的只有 `update_draft_token_ids_in_output`。后者只在 `EngineCore.step_with_batch_queue` 的 deferred 分支调用：`AsyncScheduler._update_after_schedule` 置 `pending_structured_output_tokens`，这正是默认 async 调度加结构化输出时走的路线。
- 建议：分开两条路线写，并注明 in_output 路线的触发条件是 async/PP 的 batch queue 且结构化请求有未结清 placeholder。16 §7 对同步截断的写法是对的，可以统一引用。

**F14-3 [P2] §3.5 与 §5 表：`logprob_token_ids` “同时设置时它覆盖 top-k”，没有写投机路径的例外**

- 源码：MRV2 `RejectionSampler._get_logprobs_tensors` 只用 `max_num_logprobs`，不处理 `logprob_token_ids_state`；`GPUModelRunner.sample` 的批分片 gather 以 `include_token_ids=(num_draft_tokens == 0 or rejection_sampler is None)` 调 `get_logprobs_dims`，注释为 “Rejection sampler does not return logprob token ids”。
- 影响：开投机时 generative scoring 请求的 `logprob_token_ids` 不被返回，14 和 16 都没把这点写成边界（16 §9.1 只在成本表里一笔带过）。
- 建议：在 §3.5 “其三”后加一句投机例外，并链到 16。

**F14-4 [P2] §6.4 多位置 grammar 预演 / `-1` 规则缺少可重放例子（algorithm-replay 的局部缺口）**

- `grammar_bitmask` 窗口循环是有序的 mask 规则（先 fill 当前行，再 accept，遇 `-1` 关后续，末尾 rollback）。页面只有文字，§6.2 的 FSM 图也不覆盖 spec 窗口。另有一个值得点明的细节：窗口 `[x1, -1]` 中，`-1` 那一行仍用“接受 x1 后”的状态填 mask（`_fill_bitmasks` 在判 `-1` 之前调用）；bonus 行也用同一个状态，而它其实不对应 bonus 位置。这个行为无害，因为 `-1` 必然在更早位置被拒（standard 必拒，block 截断，greedy 写 target argmax）。
- 建议：用 `ab/ac` 语言加 k=2 草稿 `[a, -1]` 画一行一格的 mask 表（row0=S0，row1=S1，bonus=S1 不可达），并说明 rollback 次数为 1。

### 3.3 Findings（页 16）

**F16-1 [P1] §5.1 表「V1 Step3.5 MTP」行：MRV2 分派条件写错**

- 页面原句：“MRV2 没有专用分支……`init_speculator` 的 `"mtp"` 分支把它当通用 `MTPSpeculator` 静默跑起来”。
- 源码：`vllm/v1/worker/gpu/spec_decode/__init__.py::init_speculator` 先判 `use_gemma4_mtp()`，再判 `use_multi_module_mtp()`，然后才是 `method == "mtp"`。`SpeculativeConfig.use_multi_module_mtp` 在 `min(num_nextn_predict_layers, num_speculative_tokens) > 1` 时为真。Step3.5 的 draft hf_config 在 `speculative.py` 中被改写为 `model_type="step3p5_mtp"`、`n_predict=num_nextn_predict_layers`，“同一 MTP 层多次 forward”的告警也专门排除了 `step3p5_mtp`，暗示它有多层。所以 k>1 且层数>1 时它走 `MultiModuleMTPSpeculator`，不是通用 `MTPSpeculator`。
- 建议：改成“MRV2 无专用分支：`min(层数,k)>1` 时落 `MultiModuleMTPSpeculator`，否则落 `MTPSpeculator`；两者都没有 V1 `Step3p5MTPProposer` 的 per-group attention metadata 接口”。

**F16-2 [P1] §5.1 变体集合与自己声明的枚举依据不一致：V1 分支不完整**

- 页面声明枚举依据包括 “V1 的 `GPUModelRunner.__init__` 分支”，但表格只列出 V1 的 n-gram/ngram_gpu/suffix、Step3.5，以及“draft_model、Medusa、custom_class 等”。
- 源码：V1 分支还有 `EagleProposer`（eagle/eagle3/mtp）、`DFlashProposer`、`Gemma4Proposer`、`ExtractHiddenStatesProposer`。当 V2 因其它 blocker（如 DBO 不支持项、elastic EP、平台）自动回退 V1 时，这些都是活路径。§8.4 讲 V1 padded drafter 时隐含依赖它们，但变体表里看不出来。
- 影响：读者无法区分“V1 不存在 EAGLE 实现”和“表格没列”，这正是 feature profile 要防的情况。
- 建议：给表加一列 “V1 实现 / MRV2 实现”，按 `GPUModelRunner.__init__` 的 if/elif 顺序完整列出，每行写明 q 的含义与选择条件。

**F16-3 [P1] §8.3「草稿发布」路线 3（async）与 §7 表 async 行、§1.2 表“草稿发布”行：漏掉 async 加结构化输出走 deferred 分支**

- 页面原句：“**async 路线。** `post_step` 被门直接跳过；`AsyncScheduler._update_after_schedule` 已经写好 `-1` 占位列表，真实候选留在设备上。”路线 2 被表述为 “batch queue 的 deferred 路线”，没有和 async 挂钩。
- 源码：`vllm/config/vllm.py::VllmConfig.max_concurrent_batches` 在 async 下返回 ≥2，所以 async 调度一定走 `EngineCore.step_with_batch_queue`（async 在兼容时默认开启）。`AsyncScheduler._update_after_schedule` 在结构化请求有未结清 placeholder 时置 `pending_structured_output_tokens`，Core 于是走 deferred：`take_draft_token_ids()` → `Scheduler.update_draft_token_ids_in_output()` → `get_grammar_bitmask()` → `sample_tokens()`。MRV2 `DraftTokensHandler.set_draft_tokens` 对这类 batch 做 D2H，`get_draft_tokens` 返回的是真实 id（`[-1]*n` 的注释写明 “only happens when async scheduling is disabled”）。
- 影响：读者会以为 async 下草稿永远不回 CPU、grammar 永远看不到真实草稿，与 14 §6.4 的预筛叙述对不上。这是 14↔16 在“grammar 与草稿”接缝上的主要 E2E 断点。
- 建议：路线 2 标题改为“async / PP 的 batch-queue deferred 路线（结构化输出时）”，路线 3 限定为“async 且本 batch 无结构化输出请求”；§7 表 async 行补上这个例外；与 14 §6.4 约定由一页做 owner，另一页只链接。

**F16-4 [P2] §1.2 表“grammar 预演与 `-1` 语义”行写“三种来源”，§3.3 写“四个来源”，§7 表列了五种情况**

- 建议统一口径：以 §3.3 的四个来源为准，§7 表是按调度情况展开的视图，两处互相注明。

**F16-5 [P2] §5.2 第 1 步：“draft 组的位置12是本轮第一次写（它的 prefill 只覆盖 draft 位置10与11）”**

- 源码：`AutoRegressiveSpeculator._prefill` 以 target 传入的 `slot_mappings` 跑整个 padded 宽度（3 行，含位置 12 的 slot）。`_prepare_prefill_inputs_kernel` 只改写前 `query_len` 行的 input_ids/positions，第 3 行保留旧 buffer 内容。**分析推断**：draft prefill 在 draft 层的 slot(12) 也写入了一条来自无效输入的 KV，decode 第 1 步再按 `compute_slot_mappings` 覆盖。“第一次写”的说法不准确，结论（最终内容正确）不变。
- 建议：改成“prefill 的第 3 行（被拒位置）写入无效 KV，decode 第 1 步覆盖同一 slot；这也是 §5.2 增量成本里‘为被拒位置付了算力’的一部分”，并标注为推断。

**F16-6 [P2] §9.1 表“用户可见 logprobs 的缺口”行**

- 页面原句：“投机路径下 `Sampler.get_logprobs_dims()` 以 `include_token_ids=False` 调用”。
- 源码：这个调用只出现在 `GPUModelRunner.sample` 的**批分片** `gather_sampler_output` 分支。普通投机路径是 `RejectionSampler._get_logprobs_tensors` 只用 `max_num_logprobs`，从不处理 `logprob_token_ids`。
- 建议：改成“rejection sampler 不产出 `logprob_token_ids`（批分片 gather 以 `include_token_ids=False` 反映这一点）”，并与 F14-3 统一 owner。
