### 1.3 Findings

- **F01-1（P1）§6.1 模型、模板与生成默认值 — `generation_config=vllm` 的语义与实现及 03 矛盾**
  - 页面：“`generation_config` 默认 `auto`……也可指定目录，或用 `vllm` 不加载该文件。”
  - 源码：`vllm/v1/engine/input_processor.py::InputProcessor.__init__` 设 `generation_config_fields = model_config.try_get_generation_config()`；`vllm/config/model.py::ModelConfig.try_get_generation_config` 在 `generation_config in {"auto","vllm"}` 时仍从模型路径读取。`vllm/sampling_params.py::SamplingParams.update_from_generation_config` 再把 `eos_token_id` 列表并入 `stop_token_ids`。跳过模型文件的只有采样缺省（`get_diff_sampling_param` 的 `config = {} if src == "vllm"`）。`ModelConfig.generation_config` 的 docstring 写 “no generation config is loaded”，与实现冲突。
  - 跨页：03 §2.2 写得是对的（“它不表示 EOS 等特殊 token 信息完全不再读取模型配置”）；04 §2.1 与 01 一样过宽。
  - 修复：改为“`vllm` 让采样缺省（temperature/top_p/top_k/min_p/repetition_penalty/max_new_tokens）不再取自模型的 generation_config.json；EOS 等特殊 token 仍从该文件读取”。加一个 `[!contradiction]` 记录 docstring 与实现冲突，并链接 03 §2.2。

- **F01-2（P1）§2.2 固定到本文源码对应的安装 — CUDA 默认变体的文档/实现冲突未记录，影响驱动前置条件**
  - 页面：“固定基线文档的默认 CUDA wheel 变体是 12.9”。
  - 源码：`docs/getting_started/installation/gpu.cuda.inc.md` 写 12.9。但 `vllm/envs.py::VLLM_MAIN_CUDA_VERSION` 默认 `"13.0"`；`.buildkite/release-pipeline.yaml` 主构建步骤为 “Build wheel - x86_64 - CUDA 13.0”，12.9 放在 `build-additional-wheels` 块步骤；`requirements/cuda.txt` 使用 `nvidia-cutlass-dsl[cu13]`、`humming-kernels[cu13]`；`docker/Dockerfile` 为 `ARG CUDA_VERSION=13.0.3`。同一文档 L327 另写 CUDA 13 需要 R580 以上驱动。
  - 说明：`wheels.vllm.ai/<commit>` 实际提供哪个变体属于外部服务，未核实。
  - 修复：加 `[!contradiction]`：文档写 12.9，而基线构建默认与依赖指向 CUDA 13.0。前置条件补“核对 `torch.version.cuda`；CUDA 13 wheel 需要 R580+ 驱动，否则用 `/cu129` 变体子目录或 `--torch-backend=cu129`”。

- **F01-3（P1）§1–§7 整体 — 使用说明内容不完备，且没有到其他能力的路由**：见 §5 覆盖表。01 只覆盖文本 chat/generate/stream。平台的主要用户能力（pooling、多模态、结构化输出、工具调用、LoRA、多卡、batch、CLI 客户端）在 01 既无场景说明，§7 也无链接。修复：§7 加一张“能力 → 使用入口页/章节”表（至少链接 02 §5.x、03 §5.x、14、15、16、17、18、22、24），或按覆盖表补场景小节。页面拆分属于 planning 决策（见 E2E 节）。

- **F01-4（P2）§6.1 — “`stop_token_ids` 还会合并服务默认停止 token”是基线内不可达的分支**
  - 源码：`ChatCompletionRequest.to_sampling_params` 有合并代码；但 `OpenAIServingChat.__init__` 的 `default_sampling_params = model_config.get_diff_sampling_param()`，该函数只产出 6 个采样键，基线内没有别处向其写入 `stop_token_ids`（`rg "default_sampling_params\s*="` 只命中各 serving 的同一赋值）。

| 下一步 | Related Pages 指向机制页 |

**要把 03 改成使用说明需要改的内容**（这是页面合同/分类变更，应交 `planning-codebase-analysis` 决定，reviewer 不自行重划）：

1. 选项 A（推荐）：03 保留为请求语义机制页（文件名 `_analysis`，index 也把它放在“具体机制问题”组），另立或扩展一个“API 使用手册”页，按 endpoint 分节：Chat / Completions / Responses / Anthropic Messages / Embeddings & Pooling / Classify / Score & Rerank / Transcription & Translation / Realtime / Tokenize & Detokenize / Render & token-in。每节写：何时用 → 启动所需 flag → 请求示例 → 关键参数（默认值/互斥）→ 响应字段 → 常见错误 → 机制链接（03 §x）。

### 5.3 Findings

- **F24-1（P1）§3.1 五类 ABI、§5.1 所有权表、§6.1 失败表、§6.2 配置表 — 漏掉 `vllm.logits_processors` entry-point 组，并与 14 矛盾**

  - 修复：§3.1 表加第 6 行（group、加载后对象 = `LogitsProcessor` 子类、决定者 = 进程内 logits processor 构建时全部加载 + `--logits-processors` FQCN、生命周期 = V1 runner 持有、失败 = 启动失败、不受 VLLM_PLUGINS 过滤、MRV2 回退）并链接 14 §x；§6.1/§6.2 相应补行。同时说明它为什么不走统一 loader（源码未给理由，需标注推断）。

- **F24-2（P1）§6.2 配置门控 — `VLLM_PLUGINS` 过滤范围写窄，导致部署误配**
  - 页面：“`VLLM_PLUGINS` | 未设置 | General 与 Endpoint 共用的 entry-point 名称过滤”。
  - 源码：`load_plugins_by_group` 对任何组都执行 `if allowed_plugins is None or plugin.name in allowed_plugins`；platform、IO processor、stat logger 也经它加载。
  - 后果：为了启用一个 endpoint 插件或 `lora_hf_hub_resolver` 而设 `VLLM_PLUGINS=<name>`，会同时静默丢掉未列名的 OOT 平台插件（如 vllm-ascend）、IO processor、stat logger，以及 `lora_filesystem_resolver` 等 general 插件。
  - 修复：改为“对所有经 `load_plugins_by_group` 加载的组（general/platform/io_processor/stat_logger/endpoint）生效；endpoint 组额外要求必须设置；`vllm.logits_processors` 不受其约束”，并加一个运维警示：设了 allowlist 就要列全所需的全部插件名。

- **F24-3（P1）§2 最小示例 — `collective_rpc("get_scheduler_config")` 在树内没有对应 worker 方法；页面也没提 endpoint+general 配对合同**
  - 页面：“处理函数通过 `EngineClient.collective_rpc("get_scheduler_config")` 读取 Worker 配置”；Mermaid 节点 “API Server → collective_rpc 得到 cfg-a 与 cfg-b”。
  - 源码：`grep -rn get_scheduler_config vllm` 无结果；`vllm/v1/serial_utils.py::run_method` 用 `getattr(obj, method)`，真实 worker 上会抛 AttributeError。测试 `tests/plugins_tests/test_endpoint_plugins.py::test_endpoint_plugin_end_to_end` 用的是 `_FakeEngineClient(rpc_result=["cfg-a","cfg-b"])`。`interface.py` 模块 docstring 与 `docs/design/endpoint_plugins.md` “Pairing with `vllm.general_plugins`” 规定：需要的 worker 方法不存在时，由配对的 general plugin 安装。
  - 修复：说明该例在真实部署下需要配对的 general plugin 注入 `get_scheduler_config`，或者换成树内已有的 worker 方法；图中 cfg-a/cfg-b 节点标“fake client（测试）”；在 §3.1 或 §2 补“endpoint 只管 HTTP 面，引擎侧能力靠 general plugin 配对”的合同。

- **F24-4（P2）§6.2 路由冲突 — vLLM 自己的文档声称插件路由“可以 shadow 核心路由”，页面没记录**
  - 源码：`EndpointPlugin.attach_router` docstring “Routes attached here can shadow core routes with the same path”；`attach_endpoint_plugins` docstring 同。页面说同路径匹配属于 FastAPI/Starlette 语义、不能从调用顺序推广，这是正确的证据边界，但应把 vLLM 的这项文档化意图列出。
  - unverified suspicion：Starlette 按注册顺序取第一个匹配，核心路由先注册，则插件路由实际无法 shadow，文档可能与行为相反。
  - 修复：加 `[!contradiction]`，列出 docstring 的主张，并注明外部依赖行为未验证。

- **F24-5（P2）§3.3 平台探测 — 决策规则没有最小例子**：补一个两候选例子，说明 OOT 优先、再次调用 factory，以及结果缓存。

- **F24-6（P2）§4 首段 — “覆盖注册表中的旧工厂”“实例化为 lora_resolvers”措辞不准**：`LoRAResolverRegistry.register_resolver(resolver_name, resolver: LoRAResolver)` 存的是实例，`OpenAIServingModels.__init__` 只做 `get_resolver` 取引用。改为“把注册表中的 resolver 实例按顺序复制成列表”。同时注明顺序 = entry-point 发现顺序，跨包不保证稳定（源码未规定顺序，属推断）。
