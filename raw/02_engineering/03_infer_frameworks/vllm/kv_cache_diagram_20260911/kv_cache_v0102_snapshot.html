vLLM 的 KV Cache 怎么存、怎么分、怎么流

先讲清 block / page 的单位、大小和显存预算，再用六张图串起跨层布局、块表、写入寻址、推理 step 与回收。

核对基线：vLLM v0.10.2 · V1 · FlashAttention / NHD · 普通全注意力模型 · 示例 B = 16

适用范围：单个 worker / GPU rank 上的布局；L 表示该 rank 实际持有的 attention 层数。主图假设一个 KV cache group、K/V 维度相同、无跨层 KV 共享、无投机解码，且使用普通 BF16/FP16 缓存。各图是独立示意快照，position 从 0 计数。版本和后端改变时，shape、stride、分组与支持的块大小需要重新核对。源码依据在文末。

block 多大，谁决定？

block_size = B 的单位是 token。由配置、平台和后端约束共同确定；B 确定后，再用模型结构与 KV dtype 算字节数。B 在池初始化后固定。

一个 page 放几个 block？

在这里，page 是块对应的存储单位，不是再装若干 block 的上一级容器。代码的单层 page 对应该层一个 block 的 B 个 token；整层 buffer 才容纳 N 份。

一个 token 的所有层连续吗？

共用一个 block_id + offset，逐层分开存。它在 L 层的同号块中各占一个 token 槽，不会把所有层拼进一个连续小块；也不需要在块表里登记 L 个编号。

先分清 token 数、单层字节数和跨层总量

名称单位 / 范围含义
block_size = Btoken / block一个逻辑块覆盖的序列位置数，例如 B = 16 覆盖连续 16 个位置。
page_size_bytes = P字节 / 层 / block / rankKVCacheSpec 的单层大小：B 个 token 的 K 与 V 合计。该计量单位并不保证 K 与 V 在地址上相邻。
一个 block_id 对应的总量 C字节 / block / rank主图单组、均匀 L 层时，C = L × P。分配一个编号，就为这 L 层一起保留对应槽位。
num_blocks = N块编号数池的容量，每层 buffer 有 N 份单层 page 的容量；不是每个请求独享 N 块。

page 的两种口径：v0.10.2 的 Hybrid KV Cache Manager 设计文档把一组层合计的块字节数也称作 page size，并明确说它不同于代码的 KVCacheSpec.page_size_bytes。本文统一用 P 指单层，C 指跨层合计。它们都不是操作系统 / CUDA 虚拟内存的硬件页；不能用“4 KiB 页”推导 KV block 大小。[1：术语]

普通 MHA / GQA / MQA，K/V 维度相同：

每层每 token：S = 2 × Hkv_local × D × e

单层一页：P = B × S

同号块跨 L 层：C = L × P

2 是 K + V；Hkv_local 是本 rank 的 KV head 数，不是 Q head 数；D 是 head_size；e 是每个 KV 元素的字节数（BF16 / FP16 为 2）。权重的量化位数不等于 KV dtype。公式只计 KV 数据，不含额外元数据、量化 scale 或布局 padding。[2：AttentionSpec]

沿用原图的 Llama-3-70B 示例：80 层、8 个 KV heads、D = 128、TP = 8、PP = 1、BF16。每个 rank 有 Hkv_local = 1，得到 S = 512 B；单 token 跨 80 层合计 40 KiB。B = 16 时，P = 8 KiB，C = 640 KiB。八个 TP rank 合计为 5 MiB / block。

这里 TP 恰好把 8 个 KV heads 分给 8 个 rank。不能对所有模型直接用 heads ÷ TP：KV heads 少于 TP 时可能复制；有 PP 时 L 只取本 stage 的层。1 KiB = 1024 B，1 MiB = 1024 KiB。

B（tokens）单层 P80 层 C / rank40 个已写 KV 的 token尾块空槽
16（主图）8 KiB640 KiB3 个 block_id；预留 1.875 MiB8 个；320 KiB / rank
32（对照）16 KiB1.25 MiB2 个 block_id；预留 2.5 MiB24 个；960 KiB / rank

B 怎么选：可通过 --block-size 指定；未指定时由平台补默认值，不能把 16 当作所有版本、后端的固定值。此版本 FlashAttention 要求 B 是 16 的倍数，还要满足平台与配置限制；这里用 16 / 32 对照。较小的 B 通常减少尾块浪费、让前缀复用更细；较大的 B 减少块表项和分配管理次数，但会改变 kernel 效率。最终用目标工作负载测吞吐、延迟与命中率。[3：配置] [4：后端]

显存先建池，请求再按块消费

01 · 启动：确定 KV 预算 M

加载权重并做 profile，从执行器显存预算中扣除非 KV 开销。gpu_memory_utilization 覆盖执行器整体，不是全部给 KV；也可显式配置 kv_cache_memory_bytes。

02 · 初始化：申请各层 buffer

均匀单组模型按 N = floor(M / C) 算块数，每层申请 N × P 字节。多个 worker 的配置会对齐到可共同使用的块数。

03 · 运行：分配与回收编号

请求从 block pool 领取编号并填块表；GPU 逐层写 KV。结束后减少引用计数，空闲编号回池。正常运行中不会每来一个 token 就新申请一段 GPU 显存。

以上 N 为不使用块数 override 时的容量公式。池还有 null / 保留块，实际请求容量需扣除它们；混合组、padding、额外预留与共享会改变记账。池内 free 增加，也不代表显存会归还给驱动或让 nvidia-smi 用量下降。[5：块数与分组] [6：显存预算] [7：buffer 初始化]

请求需要几块？无前缀共享、无 lookahead 的单组全注意力模型，覆盖 T 个 KV token 需要 ceil(T / B) 块。

B = 16：已写 40 个 token → 3 块；写 position 40（第 41 个 token）继续用尾块 offset 8。写完 position 47 时第三块才满；处理 position 48 之前需要第 4 块。一次 prefill chunk 也可能同时申请多块。

有前缀命中时，块表里的条目数不等于新分配的物理块数；共享块只能在全池显存统计中算一次。请求预留空间和已写入的有效 KV 也应分别统计。

这些下标是什么意思？从请求定位到具体 K / V

图 0 包含两部分：先用块表把请求中的位置映射为物理槽位，再在各层复用这个槽位。slot mapping 只确定“哪个块、哪个槽”，不包含层号、K/V 选择和 head。下面仍以请求 A 的 position = 40、B = 16 为例，定位它在 layer 1 的缓存。所有下标均从 0 开始。

① 请求内的位置 → 逻辑块号与块内 offset

position = 40                 # 请求 A 的第 41 个 token
B = 16                        # 一个 block 有 16 个 token 槽
logical_block = 40 // 16 = 2   # 第 3 个逻辑块，覆盖 position 32–47
offset        = 40 % 16  = 8   # 块内第 9 个槽位

// 是整数除法，% 是取余。position 是请求内的位置；offset 是块内的位置，两者不是同一个索引。

② 查 block_table → 实际分配的物理块

block_table[A][2] = 7
            │  │   └─ 物理块编号 block_id = 7
            │  └──── 请求 A 的逻辑块编号 2
            └─────── 请求 A（此处是概念写法）

逻辑块号 2 描述请求内的顺序；物理块号 7 指向池中的存储位置。不同请求的 position = 40 可以映射到不同物理块。GPU 块表通常以本批次的请求行号索引，而不是直接拿字符串 A 当数组下标；主图省略了单个 KV group 的选择。

③ block_id + offset → 扁平 slot 编号

slot = block_id × B + offset = 7 × 16 + 8 = 120

# 从 slot 可以还原物理块与块内位置
block_id = 120 // 16 = 7
offset   = 120 % 16  = 8

# 假设此 token 在本 step 的输入 token 列表中排第 0 位
slot_mapping[0] = 120

slot_mapping[i] 的 i 是本 step 展平后的输入 token 序号，不是 layer，也不是请求内 position，通常也不等于请求行号。一个 prefill 请求可以在这个列表里占多个位置；各位置的新 K/V 按对应 slot 写入缓存。

120 是槽位编号，不是 120 字节，也不是显存指针。分配了槽位也不代表已经写入有效 KV。批处理 padding 还可能使用负值表示跳过写入，此例只展示有效 token。

④ 选择 layer、K/V、head 和向量元素

先取当前层的缓存 buffer，再按五个维度索引。沿用本文的 FlashAttention / NHD 布局：

cache = kv_cache[layer]
cache.shape = (2, N, B, Hkv_local, D)

cache[kv, block_id, offset, h, d]
索引含义本例
layer先选择该层的独立 cache buffer；它不在上面五维 shape 内1，即 layer 1
kv选择 K 区或 V 区；第一维长度为 20 = K，1 = V
block_id物理块号，范围 0…N−17
offset块内 token 槽，范围 0…B−18
h本 rank 上的 KV head 编号，范围 0…Hkv_local−1TP8 示例只有一个本地 KV head，所以取 0
d该 head 向量内的元素编号，范围 0…D−1例如 5，表示第 6 个数值
:取该维度的全部内容[:, :] 取全部 KV heads 的完整向量

kv_cache[layer] 是便于解释的按层访问写法；实际程序可能用 layer name 查字典或由 attention 模块持有张量，不要求存在一个连续的六维大 tensor。

从整份 K/V，一直定位到单个数值

# 请求 A 的 position 40，在 layer 1 的全部 K / V
kv_cache[1][0, 7, 8, :, :]    # K，形状 (Hkv_local, D)
kv_cache[1][1, 7, 8, :, :]    # V，形状 (Hkv_local, D)

# 第 0 个 KV head 的完整 K 向量
kv_cache[1][0, 7, 8, 0, :]    # 形状 (D,)

# 这个 K 向量中，下标为 5 的单个数值
kv_cache[1][0, 7, 8, 0, 5]    # 一个标量

本例 Hkv_local = 1、D = 128、BF16：整份 K 为 256 B，整份 V 为 256 B，两份合计 512 B / token / 层 / rank。

和原图简写的对应关系

K[1,7,8,:,:] 对应 kv_cache[1][0,7,8,:,:]；V[1,7,8,:,:] 对应 kv_cache[1][1,7,8,:,:]。原写法的第一维是 layer，新写法先选 layer，再用 0 / 1 选 K / V。

原图的 K[...] + V[...] 只是表示“两份数据合起来构成 KV cache”，不是数值相加。图 0 现在改用 kv_cache[layer][kv,7,8,:,:]，其中 kv = 0 / 1。

请求 + position → 查块表 → (block_id, offset) ↔ slot

再选择 layer、K/V、head、向量元素 → 具体缓存数值

实际 kernel 再结合该层 buffer 的基地址、dtype 和各维度 stride，算出显存地址。文末给出了 NHD 的完整字节地址公式。写入常用 slot_mapping，attention 读取则结合 block_table、有效序列长度与 mask 访问缓存。

把容量、编号、地址和时间串起来

  • 容量：B 决定一个块覆盖多少 token；P 决定单层所占字节；C 是同号块跨本组各层的总量。启动时申请池，运行时按块分配。
  • 编号：请求的 logical block 经 block_table 映射为物理 block_id；兼容的同组层复用编号。它不是 GPU 指针，也不是 CUDA thread block。
  • 地址：定位一个元素仍需 layer / group、K 或 V、block_id、offset、head 与维度，以及真实 stride。
  • 时间：先分配槽位，再逐层计算并写 KV，attention 读取有效内容；最后采样得到的 token，要等它自己的前向才拥有 KV。
  • 回收：释放引用 → 块归池；缓存命中 → 复用内容。它们不等于每次 cudaMalloc / cudaFree，也不保证所有重复内容都去重。

NHD 主图的字节寻址展开（忽略额外 padding，索引从 0 开始）

K 地址 = base_layer + ((b × B + o) × H + h) × D × e + d × e

V 地址 = K 地址 + N × B × H × D × e

H = Hkv_local；b 为 block_id，o 为块内 token offset，h 为 KV head，d 为 head 内维度。跨层首先换 base_layer；换后端 / HND 布局则应按实际 stride 计算，不能照抄这条公式。只算 base + block_id × P 会误以为 K/V 紧挨在一整页内。

尾块空槽何时算浪费？

独占请求覆盖 T 个 KV token 时，空槽数为 ceil(T/B) × B − T，范围是 0 到 B−1；仍在生成时这些槽可以继续填。只有假设尾部余数近似均匀，平均空槽才约为 (B−1)/2，不能直接宣称每块固定浪费 B/2。共享前缀、lookahead 和滑动窗口需要另外记账。

迁移 / offload 要看实际布局

本例一个 token 的跨层 KV，以及同一层的 K/V，都不是单段相邻数据。迁移时可逐层或批量收集多段地址，也可先打包再传；具体由 connector、后端和传输接口决定。不能由这张图推出“必须逐层流水传输”或“所有 connector 都必须携带同一套 stride 字段”。

哪些情形需要重画？

MLA：缓存压缩表示与所需的 RoPE key 等数据，不能套用普通 K/V 的 2 × Hkv × D 公式；页字节数和 B 需按具体模型、dtype、后端核对。“MLA 一律 B = 64”不是通用规则。

混合注意力 / Mamba：按 KV cache group 管理块表，各组可有不同块编号与保留策略；同组共享映射，但管理器仍知道层规格和分组。不同组的层可能复用底层 buffer 的不同块位置，页对齐可能产生 padding 或调整 B。Mamba 状态也不是普通的逐 token K/V 数组。

跨层 KV 共享：指定 kv_sharing_target_layer_name 时，某些层复用目标层缓存并跳过重复写入，物理缓存份数不再等于模型层数。

其他布局与执行模式：HND、其他 attention backend、FP8/其他量化、滑动窗口、投机解码、上下文并行或特殊 connector，都可能改变 stride、预留槽位、元数据与执行顺序。
