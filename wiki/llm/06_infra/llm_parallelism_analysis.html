反向传播算子依赖关系

PyTorch autograd 如何追踪 decoder layer 的反向计算图

二、反向计算依赖核心原则

反向计算依赖前向计算的拓扑逆序：若前向中 B 依赖 A，则反向中 ∂L/∂A 依赖 ∂L/∂B。
每个算子的反向需要前向保存的激活值（activation）：Softmax 需要 softmax 输出，LN 需要 mean/rstd，Linear 需要输入 x。
残差连接（Residual Add）的梯度会分叉：grad_out 同时流向两个分支。

# megatron/core/tensor_parallel/layers.py — LinearWithGradAccumulationAndAsyncCommunication.backward() (lines 491-638) class LinearWithGradAccumulationAndAsyncCommunication(Function): @staticmethod def backward(ctx, grad_output): input, weight = ctx.saved_tensors # 前向保存的激活 (仅 input 和 weight) # 注: 前向未保存 bias / total_input / all_gather_buffer — autograd 不会保留中间结果 if ctx.sequence_parallel: # 1. 异步 AllGather input: [S/TP, B, H] → [S, B, H] handle = dist_all_gather_func(all_gather_buffer, input, group=tp_group, async_op=True) total_input = all_gather_buffer else: total_input = input # 2. 计算 grad_input = grad_output @ W [S, B, H]（dgrad，必须等 AllGather 完成） if ctx.sequence_parallel: handle.wait() # ⚠ 阻塞: dgrad 需要完整 input grad_input = grad_output.matmul(weight) # [S, B, H] @ [H, H/TP].T → [S, B, H] if ctx.allreduce_dgrad: # 3. 异步 AllReduce grad_input (可与 wgrad 计算重叠) handle = dist.all_reduce(grad_input, group=tp_group, async_op=True) # 4. 计算 grad_weight = input.T @ grad_output（wgrad，需要完整 input） grad_weight = grad_output.t().matmul(total_input) if ctx.sequence_parallel: # SP: ReduceScatter grad_input → [S/TP, B, H]（异步，与 wgrad 重叠） handle = dist_reduce_scatter_func(sub_grad_input, grad_input, ...) if ctx.allreduce_dgrad: handle.wait() # 等 AllReduce grad_input 完成 return grad_input, grad_weight, ...
显存峰值关键点：

反向时需要输入激活 x来计算 grad_weight。这要求前向的所有激活都需保留到对应反向完成后才能释放。开启 activation checkpointing 后，每个 checkpoint 粒度内的激活在反向时重新计算，以时间换空间。

Tensor Parallelism (TP) — 计算通信依赖

Megatron 风格 TP，沿 hidden_dim 或 head 维度切分权重

三、TP 基本原理：Megatron-LM Column/Row Parallel

TP 将每层的权重矩阵切分到多张 GPU。核心思想是让 Allreduce = f + g 两个共轭算子分别在前向和反向中完成通信。

TP=4 下 MLP 前向通信依赖图（Megatron-style，无 SP）

TP 前向通信依赖规则（Megatron 论文 f/g 算子）

前向: X → [f] → ColumnParallel → RowParallel → [g] → Y
f: identity (前向) / AllReduce (反向)
g: AllReduce (前向) / identity (反向)

TP 通信总量（每层）：

非SP模式: 2次 AllReduce（Attn O_proj后 + MLP Down_proj后）
SP模式: 2次 AllGather + 2次 ReduceScatter（通信量相同，但允许 SP 切分序列维度）
每次 AllReduce 数据量 = 2 × (TP-1)/TP × B × S × H × 2bytes（bf16）

Sequence Parallelism (SP) — 序列维度通信

Megatron 的 SP 通过在 TP 组内切分序列维度，减少激活显存

四、SP 如何改变通信依赖

SP 和 TP 共用同一组进程（TP group）。在非线性算子（LN、Dropout）期间，序列维度被切分（[S/TP, B, H]）；在 ColumnParallel 前，通过 AllGather 还原完整序列；在 RowParallel 后，通过 ReduceScatter 重新切分序列。

SP+TP 完整数据流（单层，TP=4，数据形状标注）
SP 反向通信顺序

∂ReduceScatter → ∂RowParallel → ∂ColParallel → ∂AllGather

即：反向时 RS→AG 变为 AG→RS（通信方向对称翻转）

∂ReduceScatter = AllGather（从 [S/4,B,H] 恢复 [S,B,H] 的梯度）
∂AllGather = ReduceScatter（将 [S,B,H] 梯度聚合并切片给各 rank）

SP 的关键优势

✓ 非线性层（LN/Dropout）的激活量减少 TP 倍
✓ 与 TP 共用进程组，不增加额外通信组
✓ 通信带宽与纯 TP 的 AllReduce 等价
✗ 需要序列长度整除 TP_SIZE
✗ FlashAttention 内部仍在本地完整序列上计算

EP 反向通信顺序（梯度流向与前向对称）
# EP 反向顺序（PyTorch autograd 自动逆序执行）: # # 1. ∂GateCombine → grad_expert_out, grad_gates # 2. ∂AllToAll₂ → AllToAll(grad_expert_out) 将梯度送回各 expert 所在 GPU # 3. ∂Expert FFN → grad_weight_expert, grad_x_dispatched (各 GPU 本地) # 4. ∂AllToAll₁ → AllToAll(grad_x_dispatched) 将梯度送回 token 原 GPU # 5. ∂Router → grad_router_weight (本地, 不需要通信) # # 关键约束: # 1. ∂AllToAll₂ 必须等待所有 expert 完成 ∂Expert 计算 # 2. 若 EP 和 TP 组合: Expert 内部还有 TP 的 AllReduce/ReduceScatter # 3. 负载不均衡 (token 数不均) 会导致 AllToAll bubble # 4. Autograd 确保: EP 通信反向顺序 = 前向通信的逆序
EP 关键挑战：

1. 负载不均衡：路由器可能将过多 token 发到同一专家，导致该 GPU 计算时间远长于其他 GPU，形成 bubble。需要 auxiliary load balancing loss 或 expert capacity 限制。
2. 通信量动态变化：AllToAll 的 send/recv counts 依赖 router 决策，每个 iteration 都不同，难以预测带宽。
3. EP+TP 组合：Expert FFN 内部可以再做 TP 切分，此时每个 EP rank 内有 TP group 通信，两层通信组嵌套。

Context Parallelism (CP) — 上下文并行

沿序列维度切分，处理超长上下文（Flash Ring Attention）

六、CP 注意力的通信依赖

CP 与 SP 不同：SP 只在非线性层切分序列，ColumnParallel 前恢复；CP 在注意力计算本身就是分布式的，每个 CP rank 只有 Q[i]（local query），需要访问其他 rank 上的 K[j], V[j]。

核心结论：
前向算子依赖是严格的线性/分叉 DAG，每个算子等待其所有输入算子完成（不同 GPU 上的 TP 并行部分除外）。
反向依赖是前向 DAG 的拓扑逆序，额外需要前向保存的激活值（或 recompute）。
TP 通信是同步障碍点（每层2次），SP 将其转换为 AG+RS 配对，通信量不变但可减少激活显存。
CP Ring Attention 通过异步 P2P 实现计算通信最大重叠，是处理超长序列最高效的方式。
EP 的 AllToAll 是最难优化的通信，因为 token 分布动态变化，无法预先 pipeline；需配合 Expert Capacity 和 load balancing loss 使用。
